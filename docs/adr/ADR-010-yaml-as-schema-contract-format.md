# ADR-010 — YAML as the Schema Contract & Configuration Format

**Status:** Accepted  
**Date:** 2026-03-02  
**Deciders:** Verity Core Team  

---

## Context

Verity requires a format for:
- **Schema contracts** (column definitions, governance policies, data quality tests).
- **Project configuration** (`verity_project_conf.yaml`).
- **Source definitions** (`models/sources.yaml`).
- **Governance policies** (`config/policies.yml`).

Alternatives: JSON, TOML, HCL (like Terraform), or a custom DSL.

---

## Decision

**All Verity configuration and schema contracts are expressed in YAML.**

---

## Rationale

### Familiarity for Data Teams

Data engineers are universally familiar with YAML from dbt, Kubernetes manifests, CI/CD pipelines (GitHub Actions), and Airflow DAG config. Switching to TOML or HCL would increase the adoption barrier without technical justification.

### dbt Compatibility by Design

Verity intentionally adopts a schema format compatible with dbt's `schema.yml`:

```yaml
columns:
  - name: email
    policy: hash
    tests:
      - unique
      - not_null
```

This lowers the migration cost for teams moving from dbt to Verity.

### Multi-Document Flexibility

YAML supports both per-model files (`stg_users.yml`) and centralized schema files (`schema.yml`) in the same directory. Verity gives per-model files higher priority, allowing teams to progressively document their models.

### Source Auto-Generation Preserves YAML

The `verity generate` smart-merge strategy reads and writes `sources.yaml` as YAML, preserving existing comments and structure. A plain JSON format would not support inline comments, which are valuable for governance annotations:

```yaml
# Auto-generated by verity generate on 2026-03-02
sources:
  - name: finance_transactions
    owner: data-ops   # PII: false
    path: data/finance/transactions.csv
```

### Serde Integration

Rust's `serde` + `serde_yaml` crate provides zero-boilerplate YAML deserialization into typed Rust structs (`ProjectConfig`, `SchemaFile`, `SourceConfig`), with clear error messages for malformed config files.

---

## Consequences

**Positive:**
- Zero learning curve for data engineers already using dbt or Airflow.
- Human-readable and diff-friendly in pull request reviews.
- Inline comments enable governance annotations right next to the schema definition.
- `serde_yaml` provides typed, validated deserialization with actionable error messages.

**Negative:**
- YAML's indentation-sensitivity is a common source of user errors (misaligned blocks silently change semantics).
- No built-in schema validation language — Verity relies on `serde` type constraints rather than a JSON Schema validator.
